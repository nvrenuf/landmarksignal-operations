# Jeeves project discovery and human completion

This update changes two launcher capabilities. It preserves Project #3's `github-project3:<project-id>:<issue-id>` keys, legacy URL deduplication, workspace hashes and archived-card behavior. Project #4 retains its verified ID and `github-project:` source namespace. The LandmarkSignal board, native worker tools and explicit **Send results to GitHub Human Review / Blocked** action remain in place.

## Project selection and import

Jeeves Launch discovers open user Projects owned by `nvrenuf` when the page loads and when Lee clicks **Refresh projects**. Discovery paginates the GitHub GraphQL connection and checks authenticated account, owner, project number and node ID. It reads only: no item is imported, queued, assigned or executed. The current selection survives a successful refresh while the project remains open; otherwise Project #3 is selected if available, then the first open project. A failed refresh preserves the previous display and shows a retryable authentication/network error.

The selector is passed to every import and result-return request. The server resolves it against the discovered catalog, and import/return recheck the exact project identity. The import query also requires one existing Status field with unique **Queued for Jeeves**, **Human Review**, **Blocked** and **Done** options. Missing configuration is displayed and import is disabled. The importer refuses it again before touching the board. It never creates or modifies a GitHub field. Project #3/#4 retain their historical source IDs even when their titles change.

## Human acceptance and GitHub completion

Lee uses **Accept & Complete** on Jeeves Launch for an original GitHub-linked intake root in native **Review**. The action requires an acceptance summary, an explicit PR merge decision, and the task-specific `ACCEPT <task-id>` phrase. If a PR merge is required, Lee supplies its exact URL; the server verifies that it was merged into the originating issue repository before accepting. A preserved `requires_pr_merge` source flag or native completion contract prevents a **No PR merge required** decision. No PR is merged automatically. For other tasks, the explicit no-PR choice is a human decision, not an inference from a worker report.

Before a remote write, the server checks the selected project, original root card, source snapshot, artifacts, GitHub account, repository, issue, project item and existing Done field option. It records a `human_accepted` task event containing the decision and reviewed evidence. It calls Hermes's native `complete_task` for the Review card. It then posts a comment with a stable marker and actual run/artifact evidence, changes only that project's item Status to Done, and closes the issue if a GitHub workflow has not already closed it. **The evidence comment precedes Project Done**, because Project #3's existing Done workflow may close the issue. A legitimately closed issue is never reopened.

If a step fails after acceptance, the card and event remain auditable. Refresh results and use **Sync completion** with the same decision. The acceptance event fixes the original evidence snapshot; a changed decision or changed artifacts are refused. A retry checks all issue comment pages for the stable marker, avoiding duplicate comments even when the initial POST succeeded but its response was lost. It rechecks Done and issue closure and skips steps already complete. Errors state which stage needs a retry. The separate Human Review result-return button remains available for unaccepted Review/Blocked work and does not imply acceptance.

A decomposed child has no matching original intake root source key and cannot reach this GitHub completion path. A historical native Done card without a `human_accepted` event also cannot use it. The generic bundled Kanban status controls are unchanged; the launcher acceptance action is the synchronized human Complete path for linked intake roots.

## Verification and rollback

The fixture suite covers discovery pagination, missing Status, selection isolation, archived-card deduplication, identity mismatches, explicit acceptance provenance, historical Done and child exclusion, required PR merge, evidence-before-Done ordering, GitHub's automatic closure path, duplicate retries and staged failures. Tests use isolated SQLite files and fake GitHub responses; they never import or close real work. The normal-account verification imports the installed modules, checks all installed hashes, discovers live project metadata and reads eligible queues/result lists only.

Run `setup_github_projects.ps1` as normal Lee. It checks the fixed Hermes revision, runs fixtures and uses `github_projects_assets.json` to refuse unknown installed bytes, back up each changed file under `landmarksignal-v1/recovery/github-projects-<id>`, install the six reviewed files and verify them. Protected files use the existing scoped maintenance path, which records and restores ACLs and gives Lee read/execute on the new helper. The installer does not edit the board or configuration. Reload `reload_github_projects_dashboard.ps1` only after its existing checks confirm the port-9119 process is the standalone dashboard and there are no running cards, worker markers or unfinished runs; other services stay untouched.

To roll back, verify the standalone dashboard is idle, read the installer recovery `paths.json`, require each current file hash to match `installed_sha256`, restore each recorded `.before` byte copy to its target, and remove only the newly added helper whose backup is null. Preserve/restore the recorded ACLs, then reload the same standalone dashboard. Do not restore the Kanban database or alter GitHub items as part of payload rollback. An acceptance already recorded or GitHub issue already closed is historical work and must be reviewed separately; rolling back code cannot erase it.

The next live acceptance check requires a real, bounded root item chosen by Lee. Fixture tests and read-only live discovery cannot establish the behavior of a real GitHub Done workflow or a live issue closure. No test in this update performs such a mutation.
